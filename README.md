# DataCenter Heat Reuse

A transferable research project for recovering data-centre heat into a swimming pool, thermal storage and district heating. Original MATLAB, Simulink, Stateflow, Python, Slovak and English documents are preserved separately from the portable application.

**Current delivery is in progress.** The annual v2 model, pool v04 and Stateflow v85 have verified Python implementations. Remaining earlier Stateflow and fault-model ports are tracked explicitly; an extracted model diagram is not a completed numerical port.

## Run

With Docker Desktop or Docker Engine running:

```sh
docker compose up --build
```

Open **http://localhost:8080**. The application includes English/Slovak UI, parameter changes, new calculations, an interactive heat-flow diagram, time-series charts, original model diagrams, source documents, saved experiments and CSV/JSON export. Change the host port with `HEAT_REUSE_PORT=8085` if necessary.

Without Docker, use Python 3.11 or newer from the repository directory:

```sh
python -m heat_reuse serve
```

The current verified application uses the Python standard library and does not require MATLAB, a MATLAB licence, cloud APIs or a GPU. Source files and input data must remain beside `heat_reuse/`; for editable installation use `python -m pip install -e .`.

## Reproduce calculations

```sh
python -m heat_reuse list
python -m heat_reuse run annual-v2 --scenario Warm45_Storage100 --output runtime/annual.json
python -m heat_reuse run pool-v04 --scenario zaklad --output runtime/pool.json
python -m heat_reuse run stateflow-v85 --scenario HP_only --output runtime/dispatch.json
python -m heat_reuse verify
```

The annual test compares 8,760 hours × 22 numerical fields against a native MATLAB C88 fixture, plus a separate v2 oracle and all five original scenario summaries. The pool test compares all eight original 672-step Simulink v04 scenarios, every exported numerical field and exact dispatcher modes. Stateflow v85 additionally passes 28 native cases, 87 retained-state steps and 120,060 full-trace comparisons across all six modes. These are numerical equivalence tests of synthetic scenarios, not measured physical validation. Legacy v22/v24/v28 MATLAB helper functions have separate executable smoke/contract checks, but are not claimed to have complete historical golden-trace parity. For v30, the original MATLAB source interpreter now matches the 23 saved native Stateflow acceptance scenarios (69 intervals, 1,863 numerical comparisons, all six modes), and reproduces 18 saved fault cases. This validates those source-defined acceptance traces, not arbitrary Stateflow engine behavior or physical equipment. See [v30 native evidence](docs/migration/2026-10-31-v30-native-parity.md).

MATLAB and Python random generators are not assumed identical. The annual model uses preserved source input records. The pool uses a packaged, source-equation-generated binary64 input profile for its first 672 intervals, with all outputs recalculated independently. This prevents platform-dependent sin/cos roundoff from spuriously switching an auxiliary 250 W pump at an analytically depleted TES state. After interval 672, inputs are generated from the original formulas and may retain libm-dependent last-bit differences. The original rounded CSV inputs are not used as simulation forcing, because their quantization also changes exact-zero branches. Input provenance and limitations remain explicit.

## Project contents

| Path | Contents |
|---|---|
| `heat_reuse/` | Portable, versioned Python calculation and HTTP interface |
| `web/` | Local interactive diagrams, controls and charts |
| `datasets/reference/` | Compressed native numerical references and provenance |
| `models/` | Original SLX block/state/function catalog with explicit migration status |
| `original/primary/` | Operational subset of the original OneDrive project |
| `original/synapse/` | Additional isolated continuation studies, including work through C100 |
| `original/obsidian/` | Project notes and supporting materials |
| `manifests/` | Full source archive mappings, exclusions and release information |
| `docs/migration/` | Current status, comparison evidence and limitations |

The complete source archive is generated by `tools/snapshot.py`: identical files are stored once by SHA-256 while every original path is retained in its manifest. Generated dependencies/caches, machine-local locks and credentials are excluded with reasons. Scientific results, old revisions, failed drafts and unique runtime outputs are preserved. The archive and its verified release location will be recorded in `manifests/release.json` when publication is complete.

Restore a downloaded complete archive into a new empty directory:

```sh
python -m tools.snapshot restore heat-reuse-source-2026-10-30.zip recovered
```

The restore tool validates object sizes, SHA-256, path safety and duplicate destinations before writing. It refuses to overwrite files. No source files on the author's machine are moved or deleted.

## Persistence and offline use

Compose stores results and the SQLite experiment index in the named `experiments` volume. `docker compose down` retains it; `docker compose down -v` deletes it. Native execution uses `runtime/` or the `HEAT_REUSE_RUNTIME` environment variable.

After a successful local build, create an offline image with `docker save datacenter-heat-reuse:local -o heat-reuse-image.tar`; the recipient can use `docker load -i heat-reuse-image.tar` and `docker compose up --no-build`. Initial builds need access to the pinned Python base image. No web CDN is used.

Original SCADA v09, MATLAB LIVE and optional MQTT/FUXA settings are preserved under `original/primary/scada_v09/`. MATLAB LIVE still requires MATLAB in its historical form. The new Python application has its own data provenance and does not masquerade as that bridge or as an operational industrial controller. Optional legacy container integrations retain their original commissioning status.
