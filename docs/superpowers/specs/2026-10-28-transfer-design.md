# Перенос DataCenter Heat Reuse в воспроизводимый репозиторий

Дата: 2026-10-28. Статус: проект решения для согласования, реализация ещё не начата.

## Назначение

Передать другому человеку все найденные материалы проекта теплостанции, включая словацкие и английские документы, исходники MATLAB/Simulink/Stateflow, Python, результаты и конфигурации контейнеров. Получатель должен запускать расчёты и интерфейс на своей машине без установленного MATLAB и получать проверяемые результаты, сопоставимые с сохранёнными оригиналами.

Пользователь прямо выбрал интерактивную графическую схему с настройками и графиками. Редактор блоков и произвольных соединений не требуется. Предложение пользователя — использовать контейнеры, если это разумно.

## Подходы и рекомендуемое решение

1. Весь набор в обычном Git: один каталог для передачи, но история переполняется результатами и повторными снимками. В наборе есть одиночные JSON порядка 169–263 МБ; техническую возможность их публикации и лимиты хостинга требуется проверить. Такой вариант не рекомендуется.
2. Репозиторий + Docker Compose + полный архив исходного состояния, приложенный к релизу: в Git находятся рабочие исходники, документы, тесты, небольшой эталонный набор и манифест архива. Все исторические прогоны и уникальные старые версии сохраняются в архиве с SHA-256. Это рекомендуемый вариант: обычный clone пригоден для запуска, а полный комплект можно скачать отдельно.
3. Репозиторий с Git LFS: возможен для бинарных моделей и больших наборов, но добавляет требования к настройке и квотам получателя. Оставить запасным вариантом, если приложить архив к релизу через доступный аккаунт не получится.

Пока это рекомендация исполнителя, а не утверждённый пользователем способ хранения. Приложение GitHub подтвердило аккаунт Fenixcrowlite. Нового репозитория ещё нет. CLI gh в PATH не найден; доступный GitHub-коннектор не предоставляет операцию создания репозитория. Исполнитель должен сначала проверить существующую локальную Git-аутентификацию без вывода секретов; если подходящего доступа нет, закончить локальный Git-пакет и указать точный оставшийся шаг для публикации.

## Вычислительная часть и полнота переноса

Не заменять проект одной упрощённой моделью. Сначала составить таблицу всех активных точек входа, семейств моделей и зависимостей. Для каждой строки зафиксировать исходную ревизию, назначение, единицы, дискретизацию, состояния, порты, начальные условия, сценарии и статус переноса.

Семейства, которые уже обнаружены:

- Базовый годовой расчёт DC → HX → HP → TES → DH → газовый резерв; сценарии температуры источника, нагрузки и накопителя, показатели энергии/эксергии и экономики.
- Бассейн 500 м³ и его интеграция с DC: v02, замкнутая диспетчеризация v04, защита v05, отказы v06, резервирование v07, измерительные сценарии v08.
- Stateflow v85 и связанные подтверждающие сценарии v86: шесть режимов, таймеры, защёлки, границы накопителя, ограничение электрической мощности и обработка событий. Исторические v22–v84 сохраняются и проходят сравнение алгоритмов. В соответствии с требованием пользователя «всё» каждый уникальный рабочий исторический алгоритм тоже должен исполняться в Python с явным выбором ревизии; одного архивного воспроизведения для него недостаточно. Для одинаковых копий и снимков достаточно одного эквивалента с таблицей соответствия.
- Совместный годовой расчёт, реальные метеовходы 2025 года, кривые COP, ограничения мощности, независимый от потребителей отвод тепла IT.
- Динамика центрального отопления: существующий Python-пилот двух объёмов воды и подготовленная интеграция dh_simulink_v02. Подготовленная версия не должна получать статус проверенной только по наличию файлов.
- Развитие A36–A69: перераспределение тепла, инерция IT, защита, компрессор, графические автоматы, задержки датчиков и отключений, импорт/экспорт телеметрии и автономные отчёты.
- Исследования от 28 октября: энергетический аудит, сезонное несоответствие тепла и спроса, накопитель с ограничениями мощности и температуры. Сохранить исходную оговорку: это отдельные синтетические исследования, а не интегрированный промышленный расчёт.

В основном исходном проекте пока не обнаружены отдельные ANFIS/нейросетевые контроллеры по именам файлов и поиску в рабочих исходниках. Слово «ум» в запросе не интерпретируется как доказательство их наличия. Во время анализа зависимостей проверить связанные материалы UMINT; если такие алгоритмы действительно входят в теплостанцию, включить код, веса, данные и процедуру воспроизведения. Не добавлять посторонние RMS/ANFIS-проекты без связи с теплостанцией.

Для каждой самостоятельной рабочей MATLAB-модели, включая уникальные исторические алгоритмы, должен быть исполняемый Python-эквивалент либо явно отражённый незавершённый пункт. Полный перенос нельзя объявлять завершённым, пока такие пункты остаются. Скрипты построения .slx могут быть заменены представлением структуры и параметров соответствующей Python-модели, а не буквальной имитацией API MATLAB. Для неработавших черновиков сохраняется исходник и честный статус; они не должны автоматически становиться поддерживаемыми моделями. Не обещать автоматический запуск произвольных файлов .slx или интерпретацию всего языка MATLAB.

Отдельная проверка документа выявила неоднозначность исторических версий. Она разрешена по прямому запросу пользователя «прям всё»: рабочие уникальные алгоритмы входят в полный перенос, а дубликаты не требуют отдельных реализаций. Дополнительного выбора пользователя по этому пункту не требуется.

Исполнитель выбирает зависимости Python после анализа существующих модулей. В первую очередь использовать уже существующие Python-ядра и стандартную библиотеку; NumPy/SciPy добавлять для необходимых расчётов и чтения MAT, с зафиксированными версиями. Использование стороннего инструмента не должно менять смысл модели или исходный шаг времени без отдельного сравнения.

## Графическая часть

В браузере показываются узлы DC, теплообменник, тепловой насос, TES, бассейн, DH, резерв и независимый отвод тепла IT. Стрелки показывают фактические потоки выбранного отсчёта; подписи содержат единицы. В отдельной области видны состояния диспетчера и переходы, активные ограничения, температуры, мощности, накопленная энергия и невязка баланса.

Пользователь выбирает семейство и ревизию, сценарий, меняет доступные параметры, запускает новый Python-расчёт, сравнивает с соответствующим сохранённым MATLAB-эталоном и экспортирует CSV/JSON. Параметры схемы привязаны к тому же вычислительному ядру, что использует CLI. Для неподдерживаемой версии запуск недоступен, причина указана явно.

Исходная SCADA v09 и MATLAB LIVE сохраняются. Основной переносимый режим использует Python. Архив v08, сохранённые прогоны v04 и новые расчёты Python имеют разные метки источника; одинаковые поля не означают одинаковую модель. Подключение промышленного оборудования в задачу не входит.

## Контейнеры и воспроизведение

Основной сценарий: docker compose up --build, затем адрес в README. Приложение запускает Python-ядро и локальную веб-панель. Docker работает без MATLAB-лицензии; оригинальные модели доступны для изучения и отдельного запуска при наличии MATLAB.

MQTT/Mosquitto и FUXA подключаются дополнительными Compose-профилями, если это необходимо для воспроизведения уже сделанной интеграции. Не считать пустую FUXA установленным и настроенным HMI. Grafana не объявляется рабочей визуализацией без настроенного источника. Зафиксировать версии образов и зависимостей после проверки доступности.

Данные, новые результаты и историк сохраняются в именованных volumes. Опубликовать инструкцию резервного копирования и восстановления. Для полностью автономного запуска предоставить отдельный экспорт проверенных образов плюс зависимости и входные данные; Docker-образы не складывать в историю Git. Обычный запуск со сборкой требует доступа к реестрам пакетов и образов.

На машине сейчас Docker CLI есть, движок Docker Desktop не отвечает; свободной RAM при проверке около 2 ГБ. Не запускать тяжёлый стек или MATLAB повторно без проверки ресурсов. Для приёмки контейнера предпочтителен чистый CI/отдельный доступный Linux Docker; если выполнить нельзя, сохранить конкретный непроверенный статус вместо заявления об успехе. Запуск инфраструктуры не должен останавливать чужие процессы и рабочую SCADA.

## Архив и документы

Сохранить все уникальные найденные проектные материалы, включая SK/EN, старые версии, неудачные эксперименты, оригинальные отчёты и результаты. Неудачные/черновые результаты должны сохранять свои статусы.

Дубликаты можно хранить один раз, если манифест позволяет восстановить каждый исходный относительный путь и проверить его содержимое. Любое такое уменьшение требует проверки SHA-256, а не совпадения имени. Указать все исключения: устанавливаемые node_modules, .git, кэши компиляции/браузера, локальные PID/locks и секреты. Исключения не удаляются с исходной машины. Нужные уникальные файлы из runtime, включая завершённые result.csv/result.json и снимки QA, переносятся отдельно; действующие базы SQLite копируются согласованным backup API.

Никакие пароли, токены, cookies, персональная OAuth-конфигурация или файлы чужих проектов не публикуются. Учётные данные получатель создаёт у себя по шаблону. Исходные научные публикации сохранить в приватной поставке с указанием происхождения; открытое распространение не предполагается автоматически.

Отдельные проверки должны выявлять отсутствующие вложения Obsidian, абсолютные ссылки, ссылки на localhost машины автора и зависимости от OneDrive. Сохранить исходные названия и языки документов, добавить рабочие индексы SK/EN. Переписывание всех русских заметок на другие языки не было запрошено.

## Приёмка

1. Состав поставки сопоставлен с каждым пунктом inventory.csv: включён, дедуплицирован с восстановлением, исключён с причиной либо отсутствует/требует решения. У каждого переданного файла есть SHA-256. Проверка распаковки восстанавливает архив и сверяет манифест.
2. Для активных MATLAB-точек входа существует таблица переноса. Все обещанные самостоятельные модели исполняются в Python, а их результаты сверяются с правильной ревизией и соответствующими исходными условиями.
3. Для дискретных моделей проверяются состояния/флаги и каждый временной отсчёт. Для численных методов заранее документируются абсолютный и относительный допуски по сигналам; их нельзя выбирать задним числом ради прохождения проверки. Отдельно проверяются балансы источника, HP, бассейна, TES, DH и независимого отвода IT.
4. Проверены нормальный режим, отсутствие источника и потребителей, насыщение TES, недостаток мощности, отключение, ошибки измерений, задержки и восстановление, там где эти сценарии поддерживает оригинал.
5. Новый пользователь на чистом окружении запускает Compose без авторских путей и MATLAB, выполняет пример и получает результаты в пределах заявленных допусков. Тест фиксирует версии зависимостей и образов, входные хэши, время и код возврата.
6. Проверены веб-схема, изменение параметров, новый расчёт, графики, сравнение с эталоном и экспорт, а также сохранение данных при перезапуске контейнеров.
7. Передан проверенный git bundle или ZIP и создан новый приватный GitHub-репозиторий, если доступ позволяет. Архив всех материалов приложен к релизу, его ссылка и контрольная сумма доступны из README. Если публикация недоступна, это незавершённый пункт, а не выполненная поставка.

## Порядок выполнения после согласования

Сначала зафиксировать полный состав и семейства моделей. Затем собрать независимую копию и архив, перенести вычисления с последовательной проверкой против исходных данных, подключить графический интерфейс и дополнительные интеграции, собрать контейнеры и проверить чистый запуск. Только после проверки содержимого и секретов публиковать новый приватный репозиторий и полный архив.

Реализационный план должен разбить перенос по семействам и сохранять видимый реестр полноты. Исторические отчёты о пройденных тестах сохраняются как исходные свидетельства; они не заменяют новый прогон тестов переносимой версии.
